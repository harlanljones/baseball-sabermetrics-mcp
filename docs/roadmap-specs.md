# Roadmap specifications

**Status: proposed.** These are forward-looking product and technical specifications, not claims about current behavior. Each item should be implemented and reviewed separately. The public roadmap is at [`ROADMAP.md`](../ROADMAP.md).

## Goals and constraints

- Preserve the current default: a local MCP stdio server querying an operator-managed SQLite database with read-only access.
- Keep ingestion separate from serving. Ingestion may write to the database; MCP query tools must remain read-only.
- Import only files supplied by the operator. Do not silently fetch, bundle, or redistribute source datasets.
- Store enough provenance to identify the source and release, without representing the software as a license verifier.
- Preserve Python 3.10+ support and the zero third-party runtime dependency default unless a separately documented optional feature requires an extra.
- Any new tools, resources, errors, and limits must be reflected in the human-readable MCP guide and generated machine-readable interface contract.

## S1. Import manifest and data-quality report

**Priority:** Stage 1. **Depends on:** the existing ingestion/provenance model.

### User need

Operators need to know which exact files produced a database, whether those files changed, and whether obvious quality problems were detected. The report must be useful without copying source records into the repository or exposing them through MCP.

### Proposed behavior

- Add a versioned JSON import manifest/report generated by an explicit CLI option, for example `--report-json PATH`; do not change the current import command's default output behavior.
- Include a manifest format version; dataset ID and display name; source URL and release/version when supplied; import timestamp; relative source path where possible; SHA-256 and byte size for each input file; table names; row counts; column names and SQLite types; and warnings.
- Report structural checks such as empty files, duplicate headers, inconsistent row widths, duplicate primary identifiers when configured, and high null rates. Checks must be source-aware and clearly labeled; heuristic findings are warnings, not proof that data is invalid.
- Allow absolute paths to be omitted or redacted. The manifest must not include source rows, credentials, or environment values.
- Record supplied license/reuse text as operator-provided metadata. Never claim that a checksum, catalog entry, or quality result confirms legal permission.
- Make reports deterministic except for explicitly time- or path-dependent fields, so operators can compare releases.

### Acceptance criteria

- A repeat import of unchanged files produces the same file hashes, schema summary, and row counts.
- Changing one input file changes its reported hash and does not rewrite unrelated source metadata.
- Reports support UTF-8 JSON and have a documented versioning policy.
- Import failure leaves the database transactionally unchanged and does not emit a success report.
- Example reports contain metadata only; documentation warns that even file paths can reveal local information.

## S2. Baseball-aware player and team discovery

**Priority:** Stage 2. **Depends on:** S1 provenance conventions and imported schemas, especially Chadwick crosswalk tables.

### Proposed MCP tools

- `find_player`: accept a name or known identifier, optional identifier system, source filter, and bounded result limit. Return candidate names, IDs, source tables, matching basis, and a score or confidence category. Preserve ties and aliases; never silently choose an ambiguous match.
- `find_team`: accept a team name, abbreviation, or source-specific team ID plus optional season/source filters. Return source-specific IDs and matching evidence.
- `get_player_season_stats`: require a player identifier and season, with optional source/table selection. Return matching rows grouped by source and table, including the identifier used and provenance reference.
- `get_team_season_summary`: require a team identifier and season, with optional source/table selection. Return available source rows and indicate when a source has no matching record.

### Contract requirements

- Use the IDs actually present in the imported source and Chadwick Register; document supported ID systems rather than inventing a universal player ID.
- Return a candidate list when a name maps to multiple people. Include all matched identifiers and the rule used to rank candidates.
- Do not merge statistics across sources unless the user selects that behavior and the response identifies every contributing table and release.
- Bound result counts and response bytes. Reject invalid seasons, unknown identifier systems, and unsafe table selection using the server's normal structured MCP error behavior.
- Treat source-authored names and text as untrusted data.

### Acceptance criteria

- Fixture coverage includes duplicate names, aliases, missing crosswalk IDs, multiple source IDs, and an empty season.
- A client can trace every returned stat row to a source, table, import, and release.
- Tool schemas appear in both the MCP interface guide and generated JSON contract.
- Existing read-only SQL protections apply to these tools as well.

## S3. Metric reference and versioned calculations

**Priority:** Stage 3. **Depends on:** S2 identity selection and a documented source/season model.

### Proposed design

- Add a `baseball://metrics` resource containing metric ID, display name, definition, formula, required input fields, supported source schemas, assumptions, constants source, formula version, and citations.
- Add `list_metrics` and `get_metric_definition` tools for clients that cannot conveniently read the full resource.
- Add calculations only after their data requirements and constants are explicit. Initial candidates: OPS and OPS+ from compatible batting tables; wOBA only when season-specific linear weights are provided and identified.
- Return calculation values together with formula version, season, inputs used, source/release, constants source, and warnings for missing or estimated values.
- Keep metric definitions separate from code paths that query raw records. Never imply that metrics are directly comparable across releases when definitions or source coverage differ.

### Out of scope for the first calculation release

- WAR or other metrics whose implementations vary substantially across providers, unless a specific formula and source are selected and documented.
- Guessing missing league constants or silently substituting constants from another season.
- Publishing upstream constants or derived material without checking the source's reuse terms.

### Acceptance criteria

- Each implemented metric has a versioned formula, required-field list, constants provenance, and at least one worked example.
- Tests cover zero denominators, missing columns, missing constants, edge seasons, and formula regression fixtures.
- Results are reproducible from the reported source rows and constants.
- The catalog clearly distinguishes raw source values from calculated metrics.

## S4. Optional Parquet ingestion

**Priority:** Stage 4. **Depends on:** S1 import reports and a benchmark against CSV ingestion.

### Proposed behavior

- Support local `.parquet` files and directories only through an optional install extra, initially evaluated with PyArrow. Keep the base package dependency-free.
- Convert supported columns into the existing SQLite import model, preserving names and nulls and recording conversion decisions in the import report.
- Do not add remote object-store access or implicit downloads in this feature.
- Define explicit limits for file size, row count, nested values, and unsupported logical types. Reject unsupported values with a path-specific diagnostic instead of silently stringifying them.

### Acceptance criteria

- Installation and use without the optional extra continue to work; a Parquet import without the extra gives an actionable message.
- Parquet and equivalent CSV fixtures yield equivalent rows for supported scalar types.
- Benchmarks record import time and database size against representative Statcast-scale fixtures before release.
- Documentation states that conversion duplicates data into SQLite and explains storage implications.

## S5. Client setup and transport compatibility

**Priority:** Stage 1 for client recipes; remote transport is deferred and conditional. **Depends on:** stable MCP interface docs.

### Client compatibility

- Maintain generic configuration plus tested, version-stamped examples for a small named set of local MCP hosts (initial candidates: Codex, Claude Desktop, and VS Code MCP support).
- Each example must show an absolute executable path and database environment variable without embedding private data or machine-specific paths in the repository.
- Distinguish “documented configuration” from “verified compatibility.” Add a host to the verified list only after an end-to-end initialize, discover, and read-only query smoke run.
- Document supported operating systems and any client-specific limitations based on actual coverage.

### Conditional Streamable HTTP proposal

- Do not add a network listener to the default command. If remote use is prioritized, expose Streamable HTTP as an explicit transport mode with local stdio remaining the default.
- Require authentication for non-loopback deployment; document TLS termination, secret handling, Origin validation, DNS rebinding protections, request/body limits, rate limits, and safe error responses.
- Reuse the same read-only query policy, result caps, tool schemas, and resource behavior as stdio.
- Do not ship an unauthenticated public server, default credentials, or an implicit cloud database connection.

### Acceptance criteria

- Client examples are tested against declared client versions and protocol revisions.
- Any new transport passes the MCP transport conformance checks and security review before it is marked supported.
- Docs explain whether clients launch a local process or connect to an operator-hosted service.

## S6. Cross-platform CI and importer hardening

**Priority:** Stage 1. **Depends on:** existing manual quality workflow.

### Proposed behavior

- Keep the full supported Python-version matrix on Linux and add macOS and Windows smoke jobs on a representative subset of Python versions.
- Exercise installation, CLI entry points, stdio protocol initialization, SQLite read-only behavior, and temporary-path handling on each OS.
- Harden ZIP imports against path traversal, symbolic-link entries, duplicate/conflicting filenames, encrypted archives, malformed central directories, excessive expanded size, and extreme compression ratios.
- Provide configurable but documented archive limits and fail before writing partial database state when an archive violates them.
- Preserve safe diagnostics: do not print file contents, secrets, or full absolute paths unless the operator requests verbose local diagnostics.

### Acceptance criteria

- CI covers Linux, macOS, and Windows and reports the exact Python versions tested.
- Fixture archives cover each rejected archive condition and confirm that no partial import remains.
- Limits are documented and produce actionable, bounded error messages.
- Existing valid Lahman, Retrosheet, Chadwick, CSV, and OpenBiomechanics fixture imports remain compatible.

## Change management

Each stage should ship through a separate pull request or a clearly isolated set of commits. Update `docs/mcp-interface.md` and `docs/mcp-interface.json` whenever the protocol surface changes. Keep the server local/read-only unless an explicitly reviewed transport proposal changes that boundary. Never attach real source datasets to pull requests or CI artifacts.
